# DFlash window-wide expert assignment design

Research proposal, 2026-10-14. No implementation or performance result is claimed here. Source line numbers refer to the research checkout and may move as other kernel experiments proceed; function names are the stable references.

## Problem and established evidence

`docs/evidence/dflash-investigation/RESULTS.md` establishes that expanded scratch avoids the old overflow/retry path and that completed GPU-pointer reuse preserves logits under fixed placement. It also establishes that GPU-only placement and unconditional all-CPU RAM misses did not produce a reliable throughput improvement. CPU merging was bit-exact against serial CPU processing under fixed placement; CPU/GPU placement changes have no universal bit-exact guarantee.

The supplied profiling baseline is approximately 63 ms verification / 33 ms routes and fetches / 9.3 ms GPU experts for two drafts, and 100 / 57 / 13 ms for four drafts. Draft counts correspond to verification windows of three and five input tokens. These are phase measurements, not a decomposition into independently removable costs: the route/fetch interval can include waits, and changing placement changes overlap and expert work.

`Glm5Model::fast_moe_window`, `src/core/glm_window.cu:471`, computes router matrix products for all members at lines 477-496, then runs each token's route, disk wait and fetch serially at lines 579-591. `moe_route_kernel`, `src/kernels/cuda/glm_fast.cu`, chooses CPU entries from each token's RAM misses using `cpu_take(f)` and aged route counts, before consulting prior window GPU pointers. A prior CPU entry has a null GPU plan pointer and cannot seed reuse. Once a first GPU copy exists, later occurrences can override their nominal CPU assignment and use it.

The GPU grouping kernel groups by pointer, not logical expert ID (`moe_win_group_kernel`, same file). Identical IDs in different scratch slots remain different groups. `win_cpu_merged`, `src/core/glm_fast_path.cu:2052`, groups CPU entries by RAM source pointer and preserves each token's expert order. Consequently, consistent assignment and one physical copy per selected GPU expert are required to expose useful sharing to either backend.

## Legal planning scope

Start with the full-layer path, `STRATA_GLM_WIN_STAGGER=0`, window sizes 3-8, expanded row scratch, complete top-k evaluation, and ordinary verification rather than the pipeline's speculative skip path. Keep all selected experts; trunk/disk/pipeline skipping must be disabled or make the planner ineligible. Keep existing resident experts on the GPU.

Each router is a function of that token's completed layer input, the router weights and the layer bias. Its scores and selection do not depend on another member's expert answer. Attention and recurrent state do have causal dependencies; leave their existing order unchanged. After the full layer inputs have been produced, all router selections may be made before any member's expert evaluation. The next layer cannot be routed early because it needs this layer's expert outputs.

The current staggered sequence is `pre(l,A), pre(l,B), post(l,A), pre(l+1,A), post(l,B), ...` (`glm_window.cu:938-967`). At the moment A's route/fetch loop runs, B's router logits have not been computed. A true full-window union would require changing this schedule and pinning buffers across the two groups; it is a separate experiment. Do not count group-local planning as full-window planning.

The first experiment should require that every selected nonresident expert has a ready RAM-table source at entry to the layer. A disk-only selected expert makes that layer use the original path. The shared disk response and `wait_seq` are reused serially today; moving all routes ahead of all waits without replacing that protocol would lose responses. RAM/resident-only eligibility avoids that redesign while measuring whether union placement is worthwhile.

## Data and execution mechanism

1. Run a read-only GPU selection pass over `W.rlog` for all T members, using the existing sigmoid, bias, stable lower-ID tie break and finite checks. Produce T x 8 IDs, exact weights or selection scores, and validity. Do not increment live sequence/counts, claim spares, write routing tables, publish ring requests, or execute any expert. Sharing the selector implementation is preferable to maintaining a second approximation.
2. Form a bounded layer union, keyed by `(layer, expert ID)`, of at most `T * 8 <= 64` entries. Record member `(token, rank)` positions, multiplicity, the initial resident pointer and RAM source, and eventual backend/copy owner. Weight blobs are immutable; activations and outputs remain per member.
3. Plan assignments, initially with the conservative exchange experiment below. Existing resident entries remain GPU. An assignment is authoritative: a forced CPU use must not subsequently be overridden by the existing previous-GPU-pointer search, and a forced GPU use must not subsequently be selected by `host_set`.
4. Materialize the original per-token plans and CPU requests in token order. Increment live counters/sequences exactly once per original token/rank. Preserve ordinary route bookkeeping and the expected/processed retirement contract. The planner's selections must not create additional counted routes.
5. For each selected transient GPU expert, select the first routed member as owner, allocate one disjoint row scratch slot, put the RAM source only in that owner's `fetch_src`, and point every GPU member to that slot. Perform one complete existing packed-blob fetch on the compute stream before any consumer. The other members' fetch sources are zero. Keep these transient pointers out of permanent `tab` and out of promotion metadata. Initial resident pointers need no copy. Continue using the existing grouped expert kernels and member combine order.
6. CPU assignments put the initial stable RAM source in each member's request and leave the GPU plan pointer null. Existing `win_cpu_merged` then groups that source once and computes each activation's answer separately. Retain each member's weight, answer slot and sequence; wait for its answer with the existing `moe_cpu_wait` before advancing the member's dependency.

For an initial implementation, retain serial route/wait/fetch ordering and add the planning pass before it. This isolates assignment benefits and avoids making prefetch readiness depend on a new stream protocol. A later RAM-only implementation can publish all plans, execute one union fetch launch, then group/compute; it should be measured separately because launch count and CPU start time change. Current `moe_fetch_kernel` accepts only one token's up-to-eight entries, so a union launch requires an explicit bounded owner table rather than passing a larger k to eight-entry state.

An allocated row-scratch capacity of at least `T * 8` guarantees room even if every selected GPU expert is distinct. At T=8 this is 64 slots; at T=3 it is 24, with the configuration's existing multiple-of-eight rule. No slot can be overwritten until all consumers of that layer finish. Full-layer planning requires no new weight allocation; it uses already reserved scratch. Resident/spare slots are boundary-owned and must likewise remain pinned until compute and service retirement finish.

## First policy: conservative eligibility and exchanges

Measure eligibility before relying on a gain. A repetition threshold by itself is insufficient because the CPU can already read a repeated expert's rows once, while today's GPU native window kernels still perform per-member dots.

Use a tiny shadow simulation of the existing route assignment, including enabled `MAYA_WIN_REUSE`, to obtain a baseline per-entry backend and distinct fetched set. This is metadata simulation only, not inference. Find an expert satisfying all of the following:

- It is nonresident with a ready RAM source at the start of the layer and occurs at least twice.
- Its baseline first occurrence is CPU, exactly one occurrence is CPU before its first GPU occurrence, and at least one later occurrence is already GPU. Thus its packed blob would already cross PCIe in the baseline.
- The early CPU member has a singleton expert assigned to a baseline GPU fetch in that same token, with a ready RAM source. That singleton has no other use anywhere in the layer.
- Changing the early repeated member to GPU and the singleton member to CPU keeps the GPU row count and CPU row count of that token unchanged. The removed CPU use must be the repeated expert's only CPU use in the baseline, so replacing it with the singleton does not destroy a CPU sharing group.
- After recomputing assignments and owner transfers, total distinct copied bytes do not increase. Require enough scratch, complete routes and valid sources; otherwise use the baseline.

Allow at most two such exchanges per layer, ordered deterministically by the repeat's multiplicity, saved singleton-copy bytes and first appearance. Re-evaluate after each accepted exchange; candidates must not overlap. Repeated and singleton experts within a layer share its packed layout, so the elementary exchange has equal per-member shape/type and CPU read cost. The exchanged repeated expert is copied into transient scratch at its earlier first use and reused at every later use. Its singleton no longer needs a GPU copy.

This is intentionally narrower than moving CPU-only repeated experts to the GPU. It does not add distinct GPU weight demand or GPU expert rows, and it preserves the amount of CPU expert work. It can still regress through earlier fetch placement, altered overlap, cache admission changes or planner overhead. It may rarely engage: prior-pointer reuse already moves all occurrences after the first GPU copy to GPU, so the opportunity is specifically the prefix of CPU occurrences before that copy. If diagnostic counts show negligible eligible exchanges, reject this policy as a main speed mechanism and proceed to measured union assignment rather than broadening it without evidence.

For the repeated expert, suppress its planned spare promotion and use transient scratch. For the singleton, suppress its planned promotion because it now runs on CPU. Recompute remaining route dispositions from the candidate schedule rather than copying baseline promotion flags: removing a promotion changes spare availability and later routing. The baseline is a comparison artifact, not a list of ownership edits to apply unchanged. Verify that the stated copy/row/work caps remain true after this recomputation; otherwise reject the exchange.

## Broader bounded union assignment

A second policy may place a CPU-only repeated expert on GPU, or keep all uses of an expert on CPU. Treat the expert's uses as one decision when possible. The per-token calibrated `cpu_take(f)` table does not, in general, admit a globally consistent expert assignment satisfying all token quotas: different token subsets can conflict. Do not claim unchanged placement or preserve quotas by silently splitting an expert's uses.

For each RAM expert e with multiplicity m, model CPU work as `C_e(m) = c_e * (1 + alpha_e * (m-1))`, and GPU work as `P_e + G_e(m)`. `P_e` is one complete packed-blob transfer, not m transfers. `G_e(m)` must be measured for the actual grouped GPU kernel and quant type; do not assume m tokens cost one matvec. `win_cpu_merged` currently uses approximate alpha values 0.2 for EXL3, 0.3 for native exact multi-row types, and 0.8 otherwise (`glm_fast_path.cu:2091`). They are scheduling heuristics, not a calibrated Mercury cost curve. Decode calibration (`cpu_c_ms`, `cpu_p_ms`) measures a different pool/workload and is only a starting estimate.

The layer objective is critical-path makespan: shared/router time + serial transfer work + GPU experts + any remaining CPU tail, with CPU service start time and two-pool load balance represented. It is not simply the sum of CPU time saved minus copy time, because CPU work can overlap transfers/GPU work and because the existing profile's route interval includes waits. Use a pessimistic estimate until layer-level measurements establish overlap.

Begin with at most two new distinct GPU copies per layer, a separate byte cap, scratch capacity bound, and a strict predicted layer-makespan improvement margin greater than planner overhead. Search deterministic single-expert moves and bounded swaps and leave the baseline when no candidate qualifies. This is a finite search over at most 64 experts; it does not need an exponential 2^64 solver. Log predicted/actual CPU tail, transfer bytes and GPU row counts so a misplaced estimate is observable. Do not deploy multiplicity>=2 as an unconditional GPU rule.

## Shadow simulation complexity and risks

The pure selector plus union scan can be O(T * n_expert * k) selection and O((T*k)^2) union/member matching; at eight tokens/k=8, the latter is at most 4096 comparisons. Selection adds launches/work and may outweigh a sparse exchange. Consider reusing the selected IDs in real routing after parity validation, rather than selecting twice indefinitely. A host readback to plan each layer would introduce a synchronization point in the expensive phase; prefer a bounded device planner and read back diagnostics only in a deliberately perturbing diagnostic mode.

The baseline shadow must emulate sequence advancement, `dcnt` increment order and the 4096-route aging boundary, CPU coldness ties favoring later ranks, `promote_min`, three spare claims, earlier-plan GPU reuse, and the effects of promotions on later RAM-miss counts. A layer-local copy of count and tier metadata is enough if the simulation represents a global aging crossing lazily for that layer; do not scan/copy all model counts every layer. There are at most eight simulated token routes. Keep the shadow state distinct from the real table and never publish simulated promotions to the service.

Duplicated routing policy is the principal maintenance hazard. Share the disposition helper between baseline simulation and real planning where feasible. Diagnostic-only baseline-versus-actual comparisons must check IDs, CPU/fetch/promotion masks and owners before depending on the simulation for policy decisions. Invalid routes, nondefault skip rules, active lookahead/prefetch, unknown CPU layouts, disk-only misses or an unsupported schedule should fall back before live mutation. If a live error occurs, propagate the existing route error; do not silently run a partial union or retry the legacy overflow path.

Spare-promotion changes also affect future-window cache contents even when current copies and arithmetic are controlled. Record this separately from the immediate layer benefit. A stricter first diagnostic can require no eligible spare promotion in the affected routes to measure transient assignment alone; this reduces engagement but avoids conflating the two effects.

## RAM backing, answers and numeric contracts

The initial RAM source is the original immutable packed backing, not an expert output or activation. Service promotion marks it `kRRelease` (`glm_fast_path.cu:3872`), but actual reclamation happens only at `fast_boundary` after compute synchronization and `processed >= expected` (`glm_fast_path.cu:4310`). It remains valid throughout the ordinary verification window. Transient staging that does not promote the expert need not retain a permanent RAM shadow or set `MAYA_RAM_SHADOW_MB`.

The separate permanent-shadow policy (`glm_fast_path.cu:4414`) can keep original RAM copies for resident GPU experts within a byte budget. Such a copy enables optional resident-on-CPU assignment only when it still has valid ownership and ready data; that is outside the first experiment. Do not fabricate RAM sources for resident experts from stale `rtab`, read a demotion still in flight, or release an original source once its first GPU fetch finishes if another CPU use remains. A source and every scratch/resident pointer must remain owned until all consumers and service work retire. Early cancellation must drain/retire these consumers before reclaiming state.

`CpuAnswer` and `MoeRequest` (`include/strata/kernels/glm_fast.hpp:234,243`) carry per-token weights, F32 activation and answer sequence. The ring has 64 slots. Eight tokens fit, but the service currently holds ring pointers until merged CPU computation; a new all-routes schedule must not permit later layers to lap those pointers. Snapshot requests or preserve the existing layer retirement barrier. An answer is a token-specific weighted sum and cannot be reused for another token that happens to select the same experts.

Selection must preserve sigmoid and bias application, stable ties, unbiased route weights, double sum/normalization and scaling (`moe_route_kernel`). Do not increment counts during selection. Reusing the same immutable packed bytes and same backend under a different fetch schedule should preserve arithmetic and is the existing scratch/reuse validation's scope. Moving an entry CPU<->GPU can change activation quantization, dot reduction, accumulation and the partition of the weighted expert sum. The grouped GPU combine retains rank order for GPU entries, while CPU contributions are aggregated and added through a separate answer; repartitioning changes addition order even if individual dot products agreed. Bit-exact logits are therefore required for schedule-only ablations, but must not be promised for new placement.

## Evidence required before proceeding

Collect per-layer logical multiplicity split by initial residency, baseline CPU-prefix/GPU-later opportunities, singleton exchange partners, distinct CPU/GPU/fetched experts, actual fetched bytes, eligible/accepted/vetoed moves and veto reasons. Separate metadata-only eligibility cost from diagnostic drains; synchronous group diagnostics are unsuitable throughput evidence.

For later implementation, validate pure selection and baseline simulation against existing routing; validate that every selected `(token,rank)` is represented exactly once by GPU, CPU or a propagated hard error; compare schedule-only plans bit-exact; compare changed placement with full logits and greedy picks, explicitly reporting tolerated differences. Exercise sizes 3-8, partial commits, reset/repeat, small expert-pool eviction pressure, cancellation and the RAM release boundary. Measure within-load no-draft controls and full verification wall time. Reject a sparse policy whose planner cost exceeds its saved fetches, even if its copy counters improve.
