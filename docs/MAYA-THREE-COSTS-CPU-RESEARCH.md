# Maya CPU scheduling research: dependencies, contention and safe experiments

2026-10-13. Read-only source/evidence research at `4f2f6e8ef93893ad4c18e2ab6ec702233f3fb7b5`.
No inference, builds, benchmarks, GPU use or engine changes were performed. This document is a design and experiment proposal, not a performance result. Keep GSQ-RCO 3.0bit Q4-attention, c=1, all eight required experts, the existing packed bytes and arithmetic. No token speculation, K4V, expert skipping, new quantization or hardware-specific CCD tuning.

## Main finding

The best first CPU experiment is to move the existing CPU computation ahead of **nonessential host route bookkeeping**, on the disk-free single-token path, while preserving retirement and ownership. The next substantive experiment is a dependency-driven CPU task batch that replaces whole-route GU/down barriers with expert readiness. A new adaptive split is worthwhile only after those changes have measured costs and only if it models concurrent memory pressure, GPU component dependencies and future residency value. Repeating the historical per-layer split or a global worker reduction is not a new mechanism.

The CPU-answer wait is a real dependency on required answers. Deleting its polling kernel or moving it earlier does not remove the computation. In particular, putting that wait into the GPU down kernel at its entry would destroy useful overlap.

## Evidence and a newly derived traffic accounting

The [latest profile](evidence/maya-decode-latest/RESULTS.md) has a warm 22.8705 ms/token loop: 9.2228 ms GPU arithmetic, 10.0879 ms expert fetch, only 0.5940 ms of their overlap, 2.9556 ms remaining CPU-answer wait and 1.156 ms with no recorded GPU activity. These are attributed intervals; CPU runtime itself is not their sum. The capture explicitly disabled CPU sampling and context-switch tracing. It does not measure worker imbalance, wakeup delay or host service substages.

Read-only analysis of `maya-churn/current-csv/routes.0`, combined with the latest `deep-layers.csv`, inferred each layer's blob size as fetched bytes / fetched expert count. Every layer yields one consistent size. The old route records reconcile with **all 256 latest scored token records** for fetched expert count, CPU expert count and fetched bytes, with zero disagreements. No new route recording was needed.

|---|---:|---:|
| GPU fetch | 39.921875 | 383.000064 |
| CPU lane | 60.4609375 | 564.155904 |
| Combined nonresident payload | 100.3828125 | 947.155968 |

CPU payload by layer group is 116.1216 MB in layers 3–5, 69.86496 MB in layers 6–8 and 378.169344 MB in layers 9–44. Blob sizes are 14,155,776, 10,813,440 and 8,257,536 bytes respectively. The first request CPU payload is 652.60032 MB/token.

This is **logical weight payload**, derived from route masks and immutable sizes. The native CPU path reads gate/up/down weight rows once for each selected expert; it does not imply measured DRAM-controller traffic, cache misses or PCIe transaction bytes. CPU activation reads, scratch, hardware prefetch and cache reuse are excluded. Moving a RAM expert from GPU fetch to CPU generally moves its packed weight read to another consumer rather than eliminating host-memory demand. Residency that removes either lane's miss has a stronger mechanism.

The [causal attribution](evidence/maya-transfer-attribution/RESULTS.md) establishes the interaction: CPU-first restored fetch bandwidth near 51 GB/s and removed 2.721 ms of fetch time, but added 4.405 ms to token wall time. Actual-address replay supports a concurrent host-memory effect; it does not identify a particular physical memory bottleneck. Eight workers versus sixteen was neutral within variation. Keep ordinary concurrency and sixteen workers as the reference.

## Actual critical path and exact source references

1. GPU routing selects the required experts, chooses CPU experts by coldness, and assigns GPU spares/scratch: [`moe_route_kernel`](../src/kernels/cuda/glm_fast.cu:3063), especially 3067–3090 and 3105–3159. The plan indexes only the number of RAM-tier experts, `(cpu_plan >> (4*f_ram)) & 15`; it does not inspect concurrent lane progress.
2. Route input, masks, IDs, weights and CPU source addresses are published to the mapped ring, with the sequence written last after system fences: [`glm_fast.cu`](../src/kernels/cuda/glm_fast.cu:3197) through 3244. CPU activation publication already uses all route-block threads. Shared SwiGLU runs in other blocks of the same routing kernel; it is not serialized host work before CPU execution.
3. The service polls the next sequence, applies an acquire fence, then enters `F->mu`: [`fast_service`](../src/core/glm_fast_path.cu:3275), polling 3310–3360, route recognition 3363–3379. It performs counters, route dumping/logging, promotion bookkeeping, count aging, prediction metadata and disk handling **before** CPU execution: 3380–3654. Transition reuse estimation has already been moved after CPU-answer publication at 3710–3716; that improvement must not be rediscovered or undone.
4. GPU fetch starts after route/disk-source readiness. Captured recurrent layers fetch the GU prefix on `F->cs`, down bytes on `F->ps`, then join before down arithmetic: [`fast_moe`](../src/core/glm_fast_path.cu:4703) through 4769. The GPU fetch does not wait for CPU route bookkeeping on a RAM-only route.
5. Native CPU execution uses the same preallocated scratch and existing ggml dots: [`lane_experts`](../src/core/glm_fast_path.cu:1664), native path 1758–1791. It quantizes the input once; runs all experts' GU rows as one pool batch; quantizes each completed hidden vector serially on the caller; runs all experts' down rows as another pool batch; finally combines experts serially in route order. The CPU path does **not** repeatedly quantize the input for each selected expert.
6. `native_gu_rows_split` calls separate gate and up dot functions per row, followed by the existing clamp/SwiGLU; `native_down_rows_split` calls one dot per output row: [`native_expert.cpp`](../src/kernels/cpu/native_expert.cpp:121) and [down](../src/kernels/cpu/native_expert.cpp:144). Those dot functions dispatch through ggml CPU traits.
7. The caller publishes the weighted answer then its exact route sequence: [`glm_fast_path.cu`](../src/core/glm_fast_path.cu:3700). [`moe_cpu_wait_kernel`](../src/kernels/cuda/glm_fast.cu:3278) waits after GPU down, fences and performs `out[e] += part[e]`. There are 42 such kernel invocations/token in the latest trace, including routes with no CPU answer required.
8. [`Workers::run`](../src/core/glm_fast_state.hpp:94) is a synchronous pool batch. It owns a generation-stamped CAS ticket, shares the job function by pointer, includes the caller and waits for all jobs. The generation protocol explicitly fixes an older straggler/index-reuse failure; preserve it. Default native job count is `threads * min(8, 48/threads)`, so sixteen threads have 48 pieces per batch (about three pieces per thread), not one expert per worker. Idle CPU workers spin for 20 ms on this lane; the service spins during decode and sleeps only after 200 ms idle by default.
9. [`fast_boundary`](../src/core/glm_fast_path.cu:3911) joins compute, checks route failure and waits for `processed >= expected` before table/RAM ownership changes. [`LayerGraphs::enqueue`](../src/core/glm_layer_graphs.hpp:23) embeds the CPU plan in the graph key; replay separately increments expected requests. Changing a captured scalar plan currently invalidates and recaptures the graph. [`fast_destroy`](../src/core/glm_fast_path.cu:3001) joins service and window lanes before freeing mapped answers/pools; any asynchronous CPU design must preserve this dependency.

## Ranked mechanisms

### 1. Put required CPU work before optional route accounting

**Design.** For `win_n==0`, `miss_mask==0`, a valid route and a nonzero CPU mask, take a bounded owned snapshot of the CPU sources, weights, activation and all metadata needed for later bookkeeping. Invoke the unchanged CPU computation and publish its answer immediately, then perform existing accounting and reuse observation in the same order they use today. Leave disk-bearing and window paths unchanged initially. The GPU can start the next layer while this service thread finalizes accounting; CPU expert sources remain alive until the completed token boundary.

This can be a simple reorder; a dedicated extra service thread is not needed for the first experiment. Do not acquire `F->mu` merely to protect CPU scratch: the one service caller already owns the single-token scratch. Preserve route error processing, future eviction observations and the single sequence increment. Do not retire `processed` before promotion/count/reuse metadata is complete. If mandatory ownership reconciliation exists for a particular path, keep that small reconciliation ahead of computation and defer only the rest.

**Why materially different.** The retained change moved transition scoring after the answer. This extends the same principle to the remaining pre-answer work, while retaining the fixed CPU/GPU assignment and byte counts. The source establishes a dependency opportunity, not its current magnitude.

**Savings bound.** Measure route-visible → CPU-start delay, `D_i`, and CPU completion → GPU consumer arrival. Same-assignment first-order exposed saving is bounded by `sum min(D_i, wait_i)`; increased contention from earlier CPU work can offset it. Removing an average 5/10/25 us from each of 42 routes is at most 0.21/0.42/1.05 ms/token before those interactions. No current capture demonstrates any of those delays. Treat 0–0.4 ms as a sensible initial screening range, not a forecast.

**Decisive experiment.** Add sampled host timestamps for recognition, mutex entry/exit, CPU start/finish, answer publication and final retirement. One baseline/candidate fixed-input paired screen with normal concurrency; confirm unchanged route IDs, CPU masks, promotions, fetch bytes and every logit. Reject if wall time does not improve or earlier CPU work lengthens fetch enough to erase the saved service delay. Rare count-aging and promotion-heavy routes should be tagged rather than averaged away.

### 2. One CPU task batch with expert readiness instead of route-wide barriers

**Design.** Allocate persistent route-owned descriptors and scratch for at most eight experts. Quantize `x` once. Publish GU row tasks with contiguous ranges; record each expert's remaining GU tasks. The last GU completion releases that expert's quantization task. That task calls the existing full-vector `native_quant_h` exactly once and releases that expert's down row tasks. After all down tasks, combine output rows in parallel, each row retaining the same sequential expert-index sum. Publish the final answer sequence only after every output row is complete.

Use a bounded ready queue or ready-stage ticket system. Workers must not block/spin waiting for an expert whose prerequisite jobs are queued behind them: that can occupy every worker and deadlock. Run the graph as **one** pool-owned batch or a new explicitly owned executor; do not recursively call `Workers::run` from a worker because `run_mu_` serializes it. All task functions/descriptors must outlive all workers, including failure and cancellation. Keep job completion and visibility separate: a counter reaching zero needs release/acquire ordering before quantization reads hidden rows or down reads quantized bytes.

**Minimal implementation using the existing pool.** Capture `active()` once and invoke `pool.run(active, scheduler_callback)` once. Each callback acts as a scheduler participant until the owned task graph is complete. It claims ready GU row descriptors, then any expert-ready quantization descriptor, then ready down rows, then combine rows. Use separate bounded claim tickets/CAS states for each stage; completion counters release the next stage. The task-descriptor storage and the scheduler callback live until `run` returns, preserving the pool's existing generation/function-lifetime contract. Idle scheduler participants may `cpu_relax` while another participant executes useful work, but must continue looking for ready tasks rather than waiting on a chosen expert. A callback that finds the entire graph complete returns; late-starting callbacks then return immediately. Preserve approximately the current 48 contiguous pieces per stage, subdividing at expert boundaries, rather than introducing hundreds of tiny dot jobs. Single-expert routes cannot benefit from overlap between different experts, so their prospective gains are limited to transition/quantization/combine costs. Instrument this distinction.

Start with expert-level hidden quantization. A later block-level quantization variant needs a separate parity proof against the actual ggml quantizer's block independence; calling a public whole-row quantizer on arbitrary fragments without that proof is unsafe. Down dot products require the entire quantized hidden vector. Partial down accumulations would change float reduction order and should not be the initial mechanism.

**Benefit.** The current route waits for the slowest GU piece across every expert before quantizing even the first ready expert. Work stealing plus ready stages can hide a delayed worker, overlap quantization with other GU work and remove the second pool publication. It can smooth memory bursts while keeping all expert weight reads. It does not eliminate 564 MB of CPU weight payload. Since formats are uniform within a layer and rows are already balanced, a large gain is not guaranteed; memory scheduling can even worsen total throughput.

**Savings bound.** Instrument GU last/median completion, quantization, down and combine. The direct removable budget is barrier imbalance + serial quantization/combine + pool transitions, clipped by exposed waits. A 20%/50% reduction of the measured warm CPU-answer wait would save at most 0.591/1.478 ms/token in the unchanged fetch schedule. Those are goalposts, not estimates of achieved CPU acceleration. A 0.2–0.8 ms wall improvement is a useful experiment target; no measured lower bound supports it yet.

**Decisive experiment.** Compare identical masks, sources, input/hidden quantized byte arrays, each GU/down output row and final CPU answer bit-for-bit across one/few/four CPU experts, all Q2_K/Q3_K/Q4_K formats and uneven row partitions. Delay a task intentionally in a CPU-only scheduling test to expose deadlock and stale-job failures. Then one paired engine screen measuring both CPU completion and GPU copy duration. If faster CPU stage timing yields unchanged/worse wall time, reject the schedule or test only one altered queue priority with evidence from its phase trace.

### 3. Assignment based on concurrent completion and component deadlines

**Dependency.** Begin after 1/2 have stable measured costs. The historical D6 per-layer plan fitted CPU/expert, fetch/expert and GPU GU/down duration, minimizing `max(CPU lane,GPU lane)` for each RAM miss count. It changed seven of 42 plans and lost throughput. Reimplementing that model with another table or worker count is insufficient.

**Design.** Build a small measured model indexed by layer/weight class, RAM miss count, candidate CPU count, component mode and CPU schedule. Model CPU finish `C(k,f)` and GPU lane finish `G(k,f)` under **their real concurrent execution**, rather than independent calibration rates. `G` includes resident arithmetic, prefix completion, GU duration, down-copy readiness and down arithmetic; down-copy/GU overlap and copy block limits are part of the topology. Add route/service overhead and a cautious residency penalty: coldest-only CPU selection preserves the current promotion heuristic, but a changed CPU count changes which hot misses get promoted and may change later traffic.

Select a candidate only if predicted completion improves by a margin larger than measured model error, with hysteresis and bounded k changes. Offline replay can propose plans but cannot establish their performance, because backend assignment can change logits/routes. For the first experiment, keep plans frozen for the whole request and fit on another workload. A truly token-adaptive policy should read a per-layer device plan table in `moe_route_kernel`; update it only at a completed token boundary. Keep its address stable so captured recurrent graphs can replay without recapture. Graph keys must include a policy schema/version while captured scalar plans are removed or correctly invalidated.

Do not update plans mid-route, redirect an expert already in a GPU plan, or reuse a scratch slot because an expert later got reassigned. Enforce disjoint CPU/fetch masks, all eight required experts covered, and unchanged source reservations. Per-expert IDs selected for CPU remain deterministic.

**Savings.** The warm CPU wait ceiling is 2.956 ms, but any extra GPU fetch/math and residency loss consumes that budget. CPU-first's 2.721 ms recovered transfer time cannot be added to it as independent free savings. The complete objective is `max(C,G)` plus subsequent dependent work. A model predicting a 1 ms reduction with an extra 50 MB upload must include roughly 1.3 ms at the current effective link rate and the changed memory interaction; otherwise it is not credible. No specific positive gain is established.

**Decisive experiment.** Record observed `(k,f)` buckets with actual CPU source bytes and GPU bytes, component deadlines and CPU finish. Try one model-selected frozen plan against baseline, plus one neighboring plan only if the first provides informative mechanism data. Hold out writing/web and cache transitions. Preserve weights and all expert requirements; backend migration is numerically different in this engine, so same-input tokens do not imply same routes. Require the existing numerical/quality gates, report every changed assignment, and keep a same-assignment schedule control. If user policy demands exact current hybrid logits, this mechanism is ineligible unless it passes that exact gate; do not quietly relax parity.

### 4. Phase-aware CPU concurrency inside a route

This is a scheduling variant of 2/3, not another global 16→8 test. During a long GU-prefix upload, bound ready memory-heavy CPU tasks; allow more when GPU computation provides useful slack or the copy finishes. Finish enough CPU work early to meet the down-combine deadline. A full CPU delay until fetch ends is the rejected serialization in the opposite direction and is unlikely to help.

Use explicit device-written, generation-stamped per-route copy-phase flags if dynamic control is needed. A copied progress flag must be published only after that component finishes. Avoid inserting host CUDA queries/events into captured paths for every expert. Executor active limits must be captured at batch start or updated through a proven protocol; `Workers::set_active` was designed for setup/idle adjustments, not arbitrary mid-batch changes that can strand jobs. Read-only model estimates may be adequate for the first static phase split and avoid new handshakes.

Measure both curves `C(active,phase)` and `G(active,phase)`. The isolated transfer opportunity near 2.7 ms is an upper reference for reducing contention, not a promised wall gain. A phase policy is useful only if its CPU finish remains early enough that exposed waits do not consume the copy saving. Test at most two targeted phase policies after instrumentation; keep it only if complete token time improves. Rank this below the simpler service reorder and expert pipeline because it adds a second feedback/visibility protocol and the neutral worker test lowers prior confidence.

### 5. Reuse activation work in exact native row kernels, after CPU stage evidence

The native split path calls ggml once for gate and once for up for every row. A paired GU microkernel can load the same Q8_K activation block/scales/sums once into registers and dot it against both weight rows, while preserving each row's integer chain, FP operations, reduction tree, clamp and `std::exp` behavior. A small multiple-row tile can similarly reuse activation state over several rows for down. Keep the existing packed Q2_K/Q3_K/Q4_K bytes and per-row outputs.

This reduces activation loads/decoding and call overhead, **not the expert weight bytes**, which dominate the derived host payload. Those activation vectors already fit in CPU caches, so claiming a 2x DRAM reduction would be false. Register pressure, instruction throughput and compiler choices can defeat the idea. No current trace establishes an inefficient ggml CPU ISA dispatch or redundant DRAM weight reads.

Neighboring Strata's [`kq_avx2.cpp`](../../Strata/src/kernels/cpu/kq_avx2.cpp:1) is an example of retaining ggml's reduction order while reusing weight-side work over multiple activations. Its multi-token benefit does not apply to c=1. Maya's [`kq_avx512.hpp`](../include/strata/kernels/cpu/kq_avx512.hpp:1) explicitly describes a many-activation Q2_K/Q3_K kernel, slower for one activation; its implementation also reports unavailable on Windows. Do not wire that prefill kernel into this decode lane as an optimization.

First inspect the linked ggml build/selected function and measure whether CPU GU/down is compute- or memory-limited with an appropriate bounded stage experiment. Use the existing CPU expert input capture privately for row parity across all three quant classes. Require exact outputs, including edge activations/clamping. Only then test the paired kernel under the full concurrent fetch workload. A faster isolated row dot is insufficient; reduced CPU duration could increase overlap pressure while it is running. Net benefit is bounded by the changed exposed CPU waits plus any measured change in fetch contention, not by total CPU runtime.

## Small opportunities and tempting changes to avoid

- Combine CPU expert answers by parallel **output-row** tasks, preserving expert-index accumulation order. This removes serial work without changing arithmetic. It belongs in 2; measure its time before expecting a material gain from a ~4096×few multiply/add loop.
- Align/partition task completion counters and CPU-answer generation metadata so work-stealing does not put unrelated counters on one hot cache line. The current `CpuAnswer` has sequence and initial answer floats near each other, but no measured coherence penalty establishes it as a bottleneck. Do not start with an allocation/layout rewrite; mapped pointer changes invalidate graph ownership and must be qualified.
- Removing the standalone CPU-wait launch can save only its fixed overhead and mapped answer read, while the readiness dependency remains. A fusion into a subsequent residual operation must preserve the existing `ffn += cpu_part` rounding before residual arithmetic. Putting the wait at the beginning of routed down prevents down work from overlapping the CPU. A 2 us/invocation hypothetical floor is only 0.084 ms/token over 42 calls; current evidence does not measure that floor.
- Worker/pool active-spin duration affects resource availability and first-route wakeup. The service's Windows 1–2 ms sleep after an idle spell can affect the first route, not a sustained warm 2.96 ms/token. Measure request-entry latency separately. Do not present idle tuning or topology/CCD affinity as an established decode solution.
- Publishing CPU work before routing knows the actual top eight would require computing unneeded experts or approximating routes. It does not fit the scope. Merged multi-token CPU kernels, speculative windows and expert omission are likewise excluded.
- The DS4 [submission experiment](../../DS4-glm/docs/evidence/glm5090/expert-transfer-submission.md) changed DMA batching without changing the full lookup/reservation path and gained no inference speed. Maya already routes and fetches on the GPU; porting DS4's host-submission optimization does not remove Maya's required CPU answer.

## Required counters and bounded decision process

Use sampled in-memory records, allocated once and flushed after inference, with route sequence/layer/CPU count/fetch count/format/component mode. Avoid per-route formatting, disk writes, near-rank routing or address recording in the headline run. Establish recorder overhead once; use identical recording on both sides of diagnostic comparisons.

Record CPU route recognition, accounting start/end, activation quantization, first/last GU completion, per-expert GU-ready, quant-h begin/end, first/last down completion, combine begin/end, answer publication and retirement. Record ready-queue occupancy, CAS attempts, tasks per worker, sleeping/waking workers, batch generations and unusually late workers. Record useful CPU expert weight payload separately from GPU fetch payload, all masks and admission state. GPU counters need route→prefix/down/whole-ready, GU/down arithmetic boundaries, answer-wait start/end and phase joins. CPU/GPU timestamp domains must be correlated through profiler calibration or separately stated; do not subtract arbitrary host clocks from GPU globaltimer values.

1. Obtain one instrumented baseline that separates service delay from actual CPU work. No extensive parameter sweep. Check per-token reconciliation and identify whether answer lateness comes primarily from service, imbalance or irreducible streaming.
2. Screen mechanism 1 while holding assignment fixed. If optional bookkeeping delay is negligible, stop that branch.
3. Screen 2 only if CPU barriers/serial work/tail imbalance provide a material budget. A row-owned combine and parallel per-expert quantization can be an intermediate control; their overheads must justify the complete task graph.
4. Fit 3/4 using concurrent measurements. Test complete dependency combinations, retaining graph capture and down-copy overlap. Reject any policy that optimizes isolated copy speed or CPU time while worsening wall time.
5. Explore 5 only with evidence that CPU dots are limiting completion and exact ggml arithmetic can be retained.

All promising changes need fixed-input first/repeated requests, unchanged all-logit parity for same-assignment changes, route/mask/byte reconciliation, and unprofiled timing. Broader qualification follows a promising screen: held-out writing/web, STOP/recovery/teardown, cold→warm transitions and the existing targeted long-context/prefill checks. Keep profiling and headline throughput distinct. No quality loss may be inferred from merely retaining eight experts if assignment changes numerical outputs.

## Lifecycle contract for every proposal

- A route's activation, weights, immutable RAM source addresses, scratch and mapped answer are owned until all its CPU tasks finish and the GPU consumes the answer. Boundary retirement must include both required answer work and metadata bookkeeping.
- Publish answer floats first, then a release fence and the exact expected generation/sequence. Device consumption keeps its system fence and sequence check. Do not reset/reuse an answer slot while a GPU wait may still read it.
- A deferred/asynchronous CPU job must own a snapshot, rather than a pointer to a ring entry that can be lapped. Ring sequence alone does not reserve an entry against overwrite. Reject queue overflow or drain synchronously; never silently skip a required CPU job.
- On cancellation or failure, stop accepting new work, retire/drain admitted jobs, join workers/service, join GPU consumers/copy streams, then free mapped answers, scratch, source tiers and graph resources. Abandoning tasks while a GPU wait still expects their generation is unsafe. Preserve existing captured stream cleanup and expected/processed accounting.
- Changing plan-table addresses, answer layouts, event ownership or task scratch pointers requires graph invalidation at a completed boundary. A stable dynamic plan table avoids scalar-plan graph churn but must have explicit versioning and lifetime.

These mechanisms can be tested independently and in the specific combinations their dependency models require. The current evidence supports ordinary overlap, reducing optional service delay and measuring required CPU work. It does not establish a route to 60 TPS from CPU scheduling alone: moving 22.871 ms to 16.667 ms requires about 6.204 ms of net savings, more than the entire attributed CPU-answer wait.

## Read-only review of the parent's early-answer prototype

During this research the parent added opt-in `MAYA_CPU_EARLY` to the working tree. The inspected guard is single-token `win_n==0 && win==0`, no disk misses, a nonzero CPU mask and a mapped answer slot. Route validation/acquire precedes it. It calls the existing synchronous CPU lane, publishes answer floats/fence/sequence, increments the same counters, skips the later CPU computation and keeps `processed` after all bookkeeping/reuse. Those dependencies preserve RAM lifetime, answer ordering and exactly-once computation for this bounded path.

The remaining robust-implementation requirement is to snapshot the request before publishing the early answer: post-answer bookkeeping, probe recording and reuse still read `rq`. The current model's 42 routes/token fit within the 64-entry ring, and the next token's boundary waits for retirement, so this fixed c=1 screen cannot lap that entry. A reusable engine implementation should not rely on that model-specific count. Copy the request/all later-consumed fields into owned storage before answer publication and use that snapshot through retirement. The early prototype also moves the NVTX route metadata mark after the CPU computation; analysis must not mistake that mark's timestamp for GPU route publication or host route recognition. No build, execution or performance conclusion was performed by this research task.

## Follow-up: Windows CPU polling currently omits PAUSE

The parent identified an additional concrete source defect worth a separate bounded experiment. At the researched HEAD, [`glmfast::cpu_relax`](../src/core/glm_fast_state.hpp:51) only emits `asm volatile("pause" ::: "memory")` for `__x86_64__ && !_WIN32`. It is an empty inline function on Windows. This differs from the separate [`ExpertPool`](../src/kernels/cpu/pool.cpp:230), which already uses `_mm_pause()` and documents a historical mistake where recording an atomic pause counter on every iteration itself caused coherence contention. The CPU expert lane under research uses `glmfast::Workers`, not that separate pool.

**Minimal implementation.** On Windows x86/x64, emit `_mm_pause()` from the helper and include the corresponding intrinsic header under an x86 Windows guard (`_M_X64`, `_M_IX86`, `__x86_64__` or `__i386__`, as applicable). `<immintrin.h>` is sufficient on the existing x64 toolchain; `<intrin.h>` is another MSVC option. Keep the Linux branch unchanged and retain an explicit no-op fallback for unsupported non-x86 targets. Do not add `Sleep`, a scheduler yield, clock queries or an atomic instrumentation counter to every spin iteration. A runtime experimental flag can isolate the change, but both baseline/candidate need the same flag-check overhead if a branch is kept inside the hot helper.

**Affected waits.** `Workers::run` polls `done_` with acquire loads; `Workers::loop` polls `gen_` with acquire loads and checks quit. The service polls the volatile mapped ring sequence. Other call sites include mapped disk read readiness, `processed >= expected` at boundaries, prefill landed readiness and window-lane queue/done waits. The main token's CUDA event loop uses `std::this_thread::yield()` directly and will not change. This is hardware-independent x86 spin hygiene, rather than a new worker assignment or CCD-affinity policy.

**Memory/progress safety.** PAUSE is a processor hint for a spin loop. It is not an acquire/release fence, a CUDA visibility operation, a notification or an OS scheduling yield. Keep every atomic load, volatile mapped read, acquire/release fence, generation ticket, wait predicate and publication store unchanged. Existing synchronization provides the happens-before/visibility relationships; the hint simply spaces polling attempts. It neither consumes a work ticket nor changes function/scratch/answer ownership. Waiting loops continue observing readiness and quit. Bounded delays between individual checks may increase slightly but the design does not depend on an exact number of spins for progress. Do not assume the intrinsic supplies the compiler memory-clobber semantics of the Linux inline assembly; use the existing atomics/volatile accesses and actual fences.

**Interaction with timed spinning.** The CPU lane's workers still use the same wall-clock 20,000 us spin budget; its default and any experimental worker count remain unchanged. Their timeout clock check is sampled every 256 loop iterations, so the interval between checks and overshoot becomes approximately 256×the new spin-loop duration rather than 256×the old duration. That increase should be measured or bounded in idle/wakeup qualification if unusual hardware makes PAUSE expensive. The service's 200 ms idle threshold is checked every 4,096 spinning polls, so it has the analogous sampling delay. Inactive workers take the `idle` branch and sleep immediately after one hint. During sustained decode, job arrivals and done/gen readiness are checked every loop, without waiting for the periodic clock check.

**Likely performance interaction, without claiming a gain.** Up to fifteen idle pool workers plus service/caller polling can compete for front-end, execution and SMT resources while useful expert work or the host launcher runs. PAUSE can reduce that pressure and repeated polling-load rate. Ordinary shared-line reads are not locked RMWs and do not themselves continuously invalidate peer caches; the done/ticket writers still create their normal coherence traffic. There is no hardware-counter evidence assigning the current deficit to this polling. PAUSE also does not remove the CPU lane's 564 MB/token weight payload, so it should not be advertised as restoring 51 GB/s host fetch by itself. On the useful dot-computation path the helper is not called; the likely benefit is worker/service tail timing and competition while waiting. The sign and magnitude remain unmeasured and may depend on placement and PAUSE latency.

**Decisive bounded screen.** Compare fixed-plan sixteen-worker normal concurrency with PAUSE alone, then combine with early CPU publication only if the standalone control is informative. Same inputs, all logits exact, route masks/byte counters exact and no recording confounder. Measure unprofiled first/repeated wall time, CPU route completion and fetch duration; measure prompt/idle-entry wakeup separately because the helper is also shared with prefill. There is no supported numeric savings estimate: direct exposed completion savings are bounded by the existing 2.956 ms warm CPU-answer wait, while any copy/launcher improvement or degradation must be observed separately. Sample timestamp/counter records at batch/route boundaries rather than instrumenting every spin. Reject a throughput claim if the difference is within run variation or CPU waits improve while whole-token time worsens. No tests, builds or experiments were performed by this follow-up research.
