# Maya missing CPU cost: completion, traffic and bounded experiments

2026-10-13. Read-only research from retained `86c6ea05d8bce5f2b42fbf0555984a652ef25827`. No inference, builds, CPU/GPU benchmarks or engine edits were performed by this research task. Source line references below refer to that checkpoint. Preserve c=1, all eight selected experts, the GSQ-RCO 3.0bit Q4-attention packed bytes, ordinary CPU/GPU concurrency and the retained early answer, PAUSE, multi-expert pipeline and prefix phase limit of eight. No CPU model, affinity, speculation, omission or quantization change is proposed.

## What is still missing

The current [results](evidence/maya-three-costs/RESULTS.md) confirm 45.90 repeated short TPS and 42.25 repeated 8K TPS. The warm diagnostic has 3.160 ms/token of remaining CPU-answer wait, 383.000 MB/token uploaded and 564.156 MB/token of logical CPU expert payload. CPU work competes with those uploads: [CPU-first](evidence/maya-transfer-attribution/RESULTS.md) recovered approximately 2.721 ms of fetch time but added 4.405 ms of token wall time. These are coupled completion costs. Restoring isolated upload bandwidth while making the CPU answer later is insufficient.

The first useful implementation is a **smaller, work-conserving executor specifically for one CPU expert**, with unchanged arithmetic and assignment. The next substantial scheduling experiment is admission of CPU weight tasks against both upload phase and CPU completion deadline. Changing CPU/GPU assignment comes after these same-assignment controls and requires a concurrent marginal-cost model, numerical qualification and graph-safe policy storage. None has an established performance gain.

## Source facts and failed experiments to preserve

- [CPU lane](../src/core/glm_fast_path.cu:1667): input quantization occurs once before native tasks. Sixteen workers normally produce `T=48` row pieces per GU batch and per down batch. The one-expert fallback uses two synchronous pool generations, caller-side whole-hidden quantization and caller-side ordered combine.
- [Retained pipeline](../src/core/glm_fast_path.cu:1765): multi-expert routes use one generation, roughly 48 GU pieces and 48 down pieces overall. Each callback scans hidden-ready experts, prefers down work, claims GU/down tasks with CAS, increments `down_done`, and claims separate combine tasks after all down work completes. GU and down use equal piece counts although GU weight bytes are twice down bytes for these layers.
- [Phase gate](../src/core/glm_fast_path.cu:1779): callback indices eight and above defer new work until the mapped `prefix_ready` word equals the route sequence. These are dynamically claimed callback indices, not physical CPU identities. After the prefix, all callbacks can compete with both down uploads.
- [Service](../src/core/glm_fast_path.cu:3464): RAM-only c=1 CPU work already precedes optional accounting, with an owned request snapshot and the live per-job phase pointer. The answer is published before bookkeeping, while `processed` remains after bookkeeping. This is retained work, not a new proposal.
- [Row kernels](../src/kernels/cpu/native_expert.cpp:121): unchanged ggml dots compute gate and up separately per row, followed by the existing clamp and `std::exp`; down computes each output dot once. [Pool](../src/core/glm_fast_state.hpp:99) uses generation-stamped tickets and waits for every callback before returning.
- [Upload DAG](../src/core/glm_fast_path.cu:4848): prefix fetch precedes GPU GU, first down-band fetch overlaps GU, first down consumes its ready band, then second down consumes the second band. The CPU answer is added after GPU down at [4921](../src/core/glm_fast_path.cu:4921). Preserve the two-band and captured-suffix dependencies.

Earlier CPU-ready tasks alone did not help; phase-aware scheduling helped only in the complete combination. `MAYA_CPU_PIPELINE_SINGLE` engaged but did not improve the combination. Global sixteen-to-eight workers was neutral. The historical D6 [per-layer split](evidence/maya-demand/RESEARCH.md) already minimized `max(CPU lane, GPU lane)` from per-expert median costs, changed only seven of 42 plans and lost throughput. More CPU experts also failed in the earlier [transfer campaign](evidence/maya-transfer/report/RESULTS.md). A new proposal must change those mechanisms, rather than rename them.

## Experiment 1: one-expert executor with coarse tasks and immediate local combine

**Implementation boundary.** Add an opt-in c=1 native `ne==1` branch after `native_quant_act` and before the existing pipeline/fallback in `lane_experts`. Require the existing per-job c=1 context; retain the original path for EXL3, windows and calibration. Leave the multi-expert pipeline/phase8 path unchanged. Use `A=pool.active()` total contiguous GU stripes and `A` down stripes, initially sixteen each instead of 48 each. Partition complete rows using the existing integer endpoint calculation. Do not apply prefix-eight gating to this branch: that was part of the rejected single-expert extension and would confound the executor comparison.

Call `pool.run(A, callback)` once. The callback first claims GU stripes from an in-range relaxed atomic ticket until exhausted. Each completed stripe decrements `gu_left` with acquire/release ordering. The last completion calls the **unchanged whole-vector** `native_quant_h`, then publishes `h_ready` with release ordering. A callback that has exhausted GU claims waits/continues until it observes hidden-ready with acquire ordering; it must not return just because GU work has been claimed.

After hidden-ready, callbacks claim down stripes, compute `native_down_rows_split`, and immediately combine their own output rows using the original expression:

```cpp
float m = 0.0f;
m += w[0] * dn[r];
out[r] = m;
```

Keep the initial addition and the materialized dot result. Do not substitute a differently fused scale/store expression or move the route weight into the dot. There is no dependency on another down stripe because only one expert contributes. Consequently this path needs **no global down-completion barrier, no combine ticket and no expert-ready scan**. A callback can return after hidden-ready is observed and all down stripes have been claimed; the pool joins every callback before the caller publishes the answer, so peers' in-flight output writes are still protected.

**Progress and memory safety.** Any participating callback can claim all GU and down stripes. Avoid a fixed initial stripe per callback or a barrier requiring all callback indices to arrive: a worker can start late, and the pool's startup generation protocol does not warrant such a barrier. Relaxed task tickets provide disjoint ownership; acquire/release GU completion carries the FF writes to the last quantizer; hidden-ready carries quantized bytes to down readers; `Workers::run` carries completed output writes to answer publication. Source/scratch/answer lifetimes remain synchronous. Preserve the pool's generation-stamped outer ticket, answer release fence/sequence and retirement protocol.

**Why this differs from failed single-expert coverage.** The baseline has 96 row jobs in two generations and serial combine. The rejected generic single-expert pipeline still has approximately 96 row tasks, per-expert scans/CAS, down-completion RMWs, separate combine scheduling and prefix gating. This experiment has 32 coarse row tasks in one generation, one hidden dependency and down-owned combine. It reduces scheduling and short-stream overhead while preserving work-conserving progress. It does **not** reduce packed weight bytes or the approximately 8,192 per-expert row-dot calls in this geometry. Longer stripes can also worsen preemption tails; no gain follows merely from fewer atomics.

**Complete bounded screen.** Compare the retained combination with only this branch enabled. Record once-per-stripe begin/end, GU remaining at hidden publication, pool generation count, and answer publication; sample rather than format/write during inference. Reconcile exact CPU/fetch/promote masks, all byte counters and every logit. Retain only if unprofiled token time improves. If the sixteen-stripe case loses through a demonstrable last-stripe tail, test one neighboring work-conserving case with 32 stripes per stage; do not launch a general split-count sweep. If neither improves, stop.

**Bound.** Direct exposed saving is at most the current **1.264604 ms/token** single-expert wait, plus or minus independently measured changes to upload contention. A 5/10 microsecond reduction per affected route is only about 0.100/0.200 ms/token. Serial combine/pool publication and tail timestamps must establish whether such a budget exists. This is a targeted low-complexity candidate, not a claim of a multi-millisecond gain.

## Experiment 2: CPU task admission with upload phases and a completion deadline

The retained prefix8 policy controls callback count until one readiness event. It does not control the packed bytes represented by each task, and it releases all callbacks while down bytes are still arriving. Current equal GU/down piece counts yield down tasks with approximately half the weight bytes; changing the generic number of workers cannot express this distinction.

**Design.** Keep CPU expert IDs and weights fixed. Replace only task admission inside the retained multi-expert executor. Precompute coarse row stripes with byte costs `2 * nf.gu_row * rows` for GU and `nf.d_row * rows` for down. Select an initial target size from the current route's bytes and active count; maintain enough ready stripes to keep admitted callbacks useful. Separate GU and down claim domains. Preserve contiguous row dots and full-expert hidden quantization; no partial-K accumulation is required.

First screen one static two-stage budget: retained admission during prefix, then a byte-based cap during the remaining down transfers, with a deadline escape that allows full admission if predicted CPU tail would miss the GPU combine arrival. The estimated deadline must include **both** down bands and GPU down; merely meeting prefix-ready is wrong. Use per-layer/format/count costs fitted on a separate workload, and conservative upper-tail CPU estimates rather than means. Check the estimate at coarse task boundaries, not every polling iteration. The escape never abandons a task or requires GPU readiness for CPU completion.

A second phase word is justified only if down contention remains material after that static screen. Publish generation-stamped first-band/whole-down readiness on the existing copy stream after the respective completion, with one stable per-job context. Extra kernels/events cost time and need a complete captured-path trial. Do not add a host CUDA query per task or mutate `Workers::set_active` inside a batch. A fused publication epilogue needs a proven last-block completion protocol; an arbitrary copy block cannot announce whole-grid readiness.

For task priority, test a single measured rule: serve the ready task on the expert's longest remaining CPU path, while reserving some GU progress until all experts have hidden-ready. The current unconditional down-first scan can postpone later experts' GU and quantization; a byte-weighted critical-path rule is a concrete alternative. It is worthwhile only if sampled traces actually show that postponement on late answers. Do not add priorities just because there is a task graph.

**Qualification and bound.** Keep early answer, PAUSE, suffix capture, two-band upload and multi-expert pipeline together. Compare whole `max(CPU answer, GPU finish)`, including changed fetch/arithmetic duration. The current multi-expert wait budget is 1.890747 ms/token; the historical 2.721 ms copy-contention recovery is an approximate separate reference, not an additional guaranteed saving. Reject if recovered upload time is consumed by CPU lateness. Gate the experiment on measured remaining down-copy contention and task-tail/priority imbalance; otherwise the retained phase8 policy already answers this question adequately.

## Experiment 3: concurrent marginal-cost CPU/GPU assignment

The existing scalar [plan](../src/core/glm_fast_path.cu:2551) uses only RAM miss count. The [router](../src/kernels/cuda/glm_fast.cu:3134) chooses the coldest eligible RAM experts for CPU and promotes fetched hot experts. The old D6 model already accounts for GPU arithmetic slack, so another per-layer median split is not new.

**New model.** For each format/layer group, RAM miss count `f`, CPU count `k`, resident count and scheduler policy, fit concurrent CPU publication `C(k)` and component durations `Pprefix`, `Pdown1`, `Pdown2`, `Ggu`, `Gdown1`, `Gdown2`. Include service/start delay. Reconstruct the existing two-band dependency DAG and minimize `max(C(k), Gfinish(k))`, rather than independent isolated per-expert rates. A candidate one-expert migration changes CPU reads, uploads, GPU arithmetic, contention, admission and future promotion; estimate its *marginal* joint completion cost and a conservative residency penalty.

For orientation, moving one 8.258 MB Q2 expert to GPU adds approximately 0.224 ms of useful upload at the retained 36.9 GB/s effective rate, before altered contention/arithmetic. Q3/Q4 give approximately 0.293/0.384 ms. Those are scales from current aggregate bandwidth, not independent route predictions. Moving the expert to CPU removes that upload but retains its host weight read. Admit a plan change only when the predicted whole completion improvement exceeds model error and qualification overhead; require hysteresis and at most a one-expert count change.

**Implementation.** Start with one request-frozen candidate plan trained on writing/web and evaluated on CSV, plus a same-assignment scheduling control. If the model does not propose a material change, stop. Only a successful frozen screen justifies a device plan table indexed by layer and miss count. Add a stable owned pointer in `MoeDev`, read it at route admission, update only after GPU/service completion at a token boundary, and include policy schema/storage ownership in graph identity. Current [graph keys](../src/core/glm_layer_graphs.hpp:14) embed a scalar plan; changing it per token recaptures graphs. Route-time choice must happen before reserving spares and filling plans, never by redirecting already admitted work.

CPU/fetch masks remain disjoint, selected experts remain covered exactly once, resident experts retain their path, and coldness tie ordering remains deterministic. Assignment changes can alter logits and subsequent routes despite fixed input tokens. Require the established full-logit numerical/quality policy; if exact current hybrid logits are mandatory and migration fails that gate, reject it. Do not interpret unchanged expert count as numerical equivalence. Validate promotion/residency over subsequent tokens, 8K lending, STOP/recovery and cold/warm transitions before retaining a policy.

## Repeated DRAM reads: what can actually be removed

There is **no demonstrated duplicate packed expert pass within a c=1 route**. Native GU visits each selected gate/up row once, native down visits each selected down row once, and CPU/fetch masks select different experts. The pipeline does not quantize the input again per expert. The 564.156 MB figure is logical packed payload, not a DRAM-controller measurement. Duplicating a pinned expert into a CPU cache arena or predecoding all weights into larger RAM buffers adds traffic/capacity and does not establish fewer DRAM reads.

CPU Q8 activation blocks are reloaded by each dot and gate/up share the same activation. These vectors fit small caches; their repeated instruction loads should not be called repeated DRAM reads. A later paired GU kernel could reuse activation decode/loads and indirect dispatch while maintaining each dot's exact integer chain, FP accumulators/reduction and clamp. The selected ggml x86 K-quant functions are in `third_party/llama.cpp/ggml/src/ggml-cpu/arch/x86/quants.c` at 1574 (Q2), 1766 (Q3) and 2038 (Q4). They already retain packed sub-blocks in registers during their expansion. Generated `build/build.ninja` rules compile ggml with `/arch:AVX512`; OFF cache booleans alone do not prove scalar dispatch. The K-quant dots still have concrete AVX2 implementations, so a broader SIMD rewrite needs its own measured instruction bottleneck and exact arithmetic proof.

Coarse task boundaries may reduce duplicated cache-line requests between workers, but only boundary lines are affected. That cannot remove hundreds of MB/token. The valuable reuse opportunity is **across token boundaries**, where the same expert may return after hundreds of MB of intervening reads. A small CPU packed-weight copy cannot guarantee that it survives in cache. Multi-token reuse changes c=1 dependencies and is outside this campaign.

Within scope, GPU residency that avoids a future CPU *or* upload miss can remove real host demand. Report combined nonresident bytes and their critical-path value, not uploaded bytes alone. Feed CPU-consumed expert IDs/bytes into the residency investigation; do not propose an unqualified extra memory tier or claim an assignment migration eliminated a read. An offline replay can quantify potential future-read avoidance but cannot establish live routes, physical cache hits or throughput.

## Experiment 4: pair independent Q2 GU dots in wide registers

This is a concrete arithmetic candidate if the executor screen leaves substantial CPU work exposed. `native_gu_rows_split` unconditionally reaches the ggml row-dot function; Maya's many-activation `kq_rows` and IQ dispatch in `native_gu_rows` are not on this c=1 split path. The ggml CPU [type table](../third_party/llama.cpp/ggml/src/ggml-cpu/ggml-cpu.c:299) maps Q2/Q3/Q4 to their Q8_K dots. Their x86 branches use 256-bit AVX2 arithmetic even in the generated AVX512 build. That is a bounded widening opportunity, rather than evidence of a scalar fallback or defective compiler flags.

**Start with Q2 GU only.** Add a dedicated source compiled with the appropriate AVX512 flags and a runtime CPU/OS feature gate, with unchanged ggml fallback. The existing [feature probe](../src/kernels/cpu/expert_layout.cpp:22) verifies OS state and additional extensions; it can conservatively gate the first prototype, though this design needs only the extensions actually used. Dispatch only `nf.gu_type==Q2_K && nt==1` from the split GU wrapper. No import of the existing many-token K-quant kernel: it allocates/unpacks temporary vectors, is documented slower at one activation, is unavailable on Windows through its current gate, and preserves outputs only up to changed floating summation order.

Represent each original Q2 256-bit chain as one half of a 512-bit register: gate in low 256, up in high 256. For each packed block, load both independent weight rows into their respective halves; load each activation vector once and duplicate it into both halves. Retain the existing low-bit expansion, per-16 scales, min correction, integer add tree and **eight FP accumulator lanes per original dot**. In each block the Q2 original applies min-correction FMA before main-data FMA; keep that order independently in both halves. After the final block, extract the two 256-bit FP halves and apply the original `hsum_float_8` tree separately. Feed the resulting scalar gate/up into the unchanged clamp/SwiGLU expression. Do not reduce sixteen lanes together, split K into independently summed halves, replace integer scaling with a different FP correction, or change `std::exp`.

This pairs *independent outputs* and widens their instruction execution, while preserving every output's original dependency and reduction tree. Packing gate/up rows that are stored in separate matrices needs two loads and register assembly; broadcasts, shuffles and register pressure may erase the saving. Merely compiling the old dot with AVX512 does not implement this mechanism.

For this geometry a Q8_K block is 292 bytes, so GU activation is 4,672 bytes and down activation is 2,336 bytes. GU currently invokes two complete dots for each of 2,048 rows and repeatedly reads the same activation. A pair reduces activation instruction loads and one indirect dot call per GU row, but leaves both packed weight rows present. Q2 CPU logical payload is approximately 378.169 MB/token of 564.156 MB/token, making it a more consequential first target than the three Q4 layers. An eventual down pair can process two output rows using the same independent-half construction; defer it until the GU case has exact parity and a useful concurrent effect. Q3 scale unpack/high-bit correction and Q4's separate min accumulator need separate arithmetic reviews, rather than a blanket type switch.

**Bounded qualification.** Use existing captured inputs and mixed-format parity facilities to compare every Q2 GU row, quantized hidden byte and expert output exactly against the selected ggml branch, including clamp boundaries and signed-zero/edge cases permitted by the existing input contract. This row check establishes arithmetic before any timing claim. Then screen the full retained combination with Q2 GU pairing alone; preserve task counts initially so its effect can be distinguished from executor changes. Record CPU answer timing and upload timing together. No isolated row speedup qualifies retention. Direct CPU wait savings remain bounded by the affected Q2-route wait; contention changes are measured separately. Only a useful exact GU result justifies pairing down or combining with the coarse executor.

**Alignment is not a traffic cure.** Q2 GU rows are 1,344 bytes and Q3 GU rows 1,760 bytes; Q2/Q3 down rows are 672/880 bytes. Some row starts are not aligned to cache-line or 256-bit boundaries, and ggml correctly uses unaligned loads. Changing to aligned intrinsics without proof is invalid. Coarse boundaries can be rounded to whole rows whose byte offset is cache-line aligned when convenient, but the amount affected is boundary lines, far smaller than packed payload. A wholesale repack or padding of every row introduces new capacity, ownership and copy-layout costs; do not append it to this experiment without a measured split-load bottleneck.

## Decision sequence and limits

1. Screen the exact single-expert coarse executor; parent implementation can proceed directly from Experiment 1. Confirm the mechanism and unprofiled wall time before tuning another path.
2. Collect sampled completion/task records on the retained multi-expert path. Proceed with byte/deadline admission only when late CPU tasks and down-transfer contention expose a budget. Test the complete dependency combination.
3. Fit concurrent marginal assignment costs from admitted variants. Try one frozen policy only when its predicted gain exceeds error. Preserve a same-assignment control and the existing numerical gate.
4. If CPU work remains substantial, screen exact Q2 GU pairing using Experiment 4. Investigate physical-read reuse only after measurements establish a duplicated physical pass; this audit found none.

For every promising case compare first/repeated fixed histories, complete logits, ordered expert IDs/masks, all payloads, ownership and unprofiled forward time. Optional CPU-stage NVTX spans are separately enabled today and must stay out of headline throughput. Allocate sampled buffers once, flush after inference and correlate host/GPU clock domains before subtracting timestamps. Preserve acquired route snapshots, exact answer generations, boundary retirement, pool joins and captured stream cleanup. On cancellation drain admitted work before releasing sources, scratch or mapped answers.

Eliminating the current CPU-answer wait alone cannot justify 60 TPS. The confirmed repeated short loop is approximately 21.786 ms/token; 60 TPS requires 16.667 ms, about 5.119 ms less. The diagnostic CPU wait is only 3.160 ms and comes from a different measurement mode. Coupled reductions to CPU completion and host traffic could contribute more, but these ceilings must not be added as independently available gains. The experiments above define mechanisms and rejection conditions, not a throughput forecast.
